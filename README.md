# FunPay Analytics

Веб-приложение для сбора и анализа заказов продавца на **FunPay**. Проект объединяет backend API и frontend-интерфейс: получает данные о заказах, сохраняет их в базе данных и отображает сводную статистику.

> **Статус проекта:** учебный / portfolio-проект. Текущая версия демонстрирует архитектуру full-stack приложения и базовый сценарий интеграции с FunPay. Перед использованием в production требуется завершить доработку авторизации и изоляции данных пользователей (см. раздел «Ограничения текущей версии»).

## Возможности

- Регистрация и вход пользователей.
- Получение заказов FunPay по `golden_key`.
- Сохранение заказов в базе данных.
- Пропуск уже сохранённых заказов при повторной синхронизации.
- Просмотр списка заказов с пагинацией.
- Расчёт основных показателей:
  - общая выручка;
  - количество заказов;
  - средний чек;
  - время последней синхронизации.
- Отображение статистики и динамики выручки в интерфейсе.
- REST API с интерактивной документацией Swagger.

## Архитектура

Проект разделён на две основные части.

### Backend

Backend реализован на FastAPI и организован по слоям:

- `app/api/routes/` — HTTP-маршруты авторизации, заказов и синхронизации.
- `app/core/` — конфигурация приложения и функции безопасности.
- `app/database/` — подключение к БД и управление сессиями SQLAlchemy.
- `app/models/` — ORM-модели пользователей, аккаунтов FunPay и заказов.
- `app/services/` — бизнес-логика обработки заказов и парсер FunPay.
- `app/schemas.py` — Pydantic-схемы запросов и ответов.

### Frontend

Клиентская часть реализована на React:

- `src/components/` — компоненты дашборда, статистики, таблицы заказов и настроек.
- `src/services/api.js` — взаимодействие с backend API.
- `src/store.js` — глобальное состояние приложения на Zustand.
- `src/hooks.js` — пользовательские React hooks.
- `src/styles/` — общие стили.

## Запуск локально

### Требования

- Python 3.11 или новее.
- Node.js 18 или новее и npm.
- Git.

По умолчанию backend использует SQLite. Для базового локального запуска отдельно устанавливать PostgreSQL и Redis не требуется.

### 1. Клонирование проекта

```bash
git clone <repository-url>
cd funpay-analytics-main
```

### 2. Запуск backend

```bash
cd backend

# Windows PowerShell:
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# macOS / Linux:
# python3 -m venv .venv
# source .venv/bin/activate

pip install -r requirements.txt
```

Создайте файл `.env` на основе `.env.example`:

```bash
# Windows PowerShell
Copy-Item .env.example .env

# macOS / Linux
# cp .env.example .env
```

Перед запуском задайте собственные `SECRET_KEY` и `ENCRYPTION_KEY`. Не используйте демонстрационные значения из конфигурации в реальном развёртывании. Для Fernet-ключа можно сгенерировать значение командой:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Запустите API из каталога `backend`:

```bash
uvicorn app.main:app --reload --host 127.0.0.1 --port 8001
```

После запуска:

- API: `http://localhost:8001`
- Swagger UI: `http://localhost:8001/docs`
- ReDoc: `http://localhost:8001/redoc`
- Health check: `http://localhost:8001/health`

### 3. Запуск frontend

Откройте второй терминал:

```bash
cd frontend
npm install
```

Создайте локальный файл `.env` на основе `.env.example` и проверьте адрес API:

```env
VITE_API_URL=http://localhost:8001/api
```

Запустите frontend:

```bash
npm run dev
```

Vite выведет локальный адрес приложения — по умолчанию `http://localhost:5173`.

### 4. Сборка frontend

```bash
cd frontend
npm run build
```

Готовая сборка будет помещена в `frontend/dist/`.

## Основные API-маршруты

Все маршруты backend доступны с префиксами, указанными ниже.

| Метод | Endpoint | Назначение |
|---|---|---|
| `POST` | `/api/auth/register` | Регистрация пользователя |
| `POST` | `/api/auth/login` | Вход и получение JWT |
| `GET` | `/api/auth/me` | Информация о текущем пользователе |
| `POST` | `/api/sync` | Синхронизация заказов с FunPay |
| `GET` | `/api/orders` | Получение списка заказов |
| `GET` | `/api/stats` | Получение агрегированной статистики |
| `DELETE` | `/api/orders/clean-duplicates` | Удаление дубликатов заказов |

Для интерактивного просмотра схем, параметров и ответов используйте Swagger UI: `/docs`.

## Конфигурация

Backend читает настройки из `backend/.env`. Основные переменные:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Строка подключения к БД |
| `SECRET_KEY` | Секрет для подписи JWT |
| `ALGORITHM` | Алгоритм подписи JWT |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Время жизни access token |
| `ENCRYPTION_KEY` | Ключ Fernet для шифрования `golden_key` |
| `CORS_ORIGINS` | Разрешённые frontend-origin |
| `API_HOST` | Адрес, на котором запускается API |
| `API_PORT` | Порт backend |
| `DEBUG` | Режим отладки |
| `FUNPAY_BASE_URL` | Базовый адрес FunPay |
| `FUNPAY_TIMEOUT` | Таймаут HTTP-запроса к FunPay |
| `LOG_LEVEL` | Уровень логирования |

Frontend использует переменную `VITE_API_URL` из `frontend/.env`.

## Работа с данными и безопасность

- Пароли в основной реализации backend хешируются с помощью bcrypt.
- Для авторизации используется JWT.
- Для хранения `golden_key` предусмотрено шифрование Fernet.
- Данные заказов сохраняются через SQLAlchemy.
- Повторная синхронизация проверяет наличие заказа по его идентификатору.
- Секреты и локальные `.env`-файлы не должны попадать в репозиторий.

**Важно:** `golden_key` предоставляет доступ к аккаунту FunPay. Не публикуйте его, не добавляйте в README, скриншоты, issue или Git-репозиторий. Используйте только собственный ключ и храните его в секрете.

## Ограничения текущей версии

Перед production-развёртыванием необходимо устранить следующие ограничения, обнаруженные в исходном коде:

1. В маршрутах заказов и синхронизации `user_id` сейчас задан фиксированным значением `1`. Получение пользователя из JWT должно быть подключено ко всем защищённым маршрутам, а операции с заказами должны выполняться только в контексте текущего пользователя.
2. В `SecurityService` при некорректном `ENCRYPTION_KEY` предусмотрен fallback без шифрования. Для production следует завершать запуск с ошибкой конфигурации, а не сохранять ключ в открытом виде.
3. В `backend/main.py` находится отдельная старая реализация API. Основная точка входа проекта — `app.main:app` (используется также в Dockerfile). Старый файл не следует использовать как команду запуска.
4. Парсер зависит от HTML-разметки FunPay. При изменении сайта потребуется обновление селекторов и проверка корректности извлечённых данных.
5. В репозитории присутствует Docker Compose для PostgreSQL и Redis, но он не описывает полный запуск frontend + backend. Основной локальный сценарий запуска приведён выше.

Поэтому проект следует рассматривать как демонстрационную версию, а не как готовый к публичной эксплуатации сервис.
